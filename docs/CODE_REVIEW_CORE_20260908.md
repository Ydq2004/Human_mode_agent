- **审查日期**：2026-09-08
- **审查发起者**：柳如烟（Agent 具身实例）
- **审核引擎**：高级模型代码审查服务（GPT / Codex 架构）
- **审核范围**：`core/`、`tools/` 模块（共扫描 22 个文件，约 221,211 字节）
- **审查重点**：代码结构、异常处理规范、后台任务生命周期与工具调用的超时/容错机制

---

## 审查概要

本次审查重点排查了异步后台任务（Background Task Worker）、具身与视觉工具服务、以及数据提交/账本同步链路中的潜在可靠性隐患。
共发现 **5 项** 与超时控制、状态管理及异常处理相关的问题，其中 **高风险 2 项**、**中风险 3 项**。

---

## 详细问题与改进建议

### 1. 【高风险】后台任务缺乏全局墙钟超时，无法中断阻塞的 Handler
- **涉及文件**：
  - `core/background_task_worker.py:70-96`
  - `core/advanced_model_service.py:245-276`
  - `tools/background_task_tools.py:88-114`
- **问题现状**：
  - `BackgroundTaskWorker._run` 仅在同步调用 `result = handler(task)` **执行完成返回后**，才计算耗时并判断是否超时。
  - `start_code_review` 创建任务时只设置了 `max_attempts=2`，未在 `request` 中注入任务级的 `timeout_seconds` 或整体 Deadline。
  - `run_code_review` 最多支持 `REVIEW_MAX_ROUNDS` 轮模型与工具调用，单次 LLM 超时只能保护单个网络请求，无法限制整个任务的总生命周期。
- **潜在危害**：
  若审核模型、网络代理或复杂工具调用陷入长时间阻塞或死循环，Worker 线程执行槽位将被长期占死，无法响应外界的取消请求。
- **改进建议**：
  1. 在任务提交及创建时注入统一的 `timeout_seconds` 或截止时间戳。
  2. 在多轮执行循环（如 `run_code_review` 的每轮模型交互与工具调用前）显式检查 Deadline，一旦超时立即终止并返回显式超时状态。
  3. 对不可中断的长时间同步任务，考虑引入可中断的边界控制或基于进程/线程超时的安全包装。

---

### 2. 【高风险】任务创建后提交 Worker 失败将遗留永久 `queued` 僵尸任务
- **涉及文件**：
  - `tools/background_task_tools.py:104-123`
- **问题现状**：
  - 系统先执行 `store.create_task(...)` 完成持久化，紧接着执行 `runtime.worker.submit(task["task_id"])`。
  - 若 Worker 已关闭抛出 `RuntimeError` 或线程池提交失败，该段代码未捕获提交异常，也未将已创建的任务状态回滚或转为 `failed`。
- **潜在危害**：
  异常直接向主循环冒泡抛出，而数据库中的任务将永久卡在 `queued` 状态，无法调度也无法自动清理。
- **改进建议**：
  1. 将“创建任务”与“提交调度”包裹在完整的 `try...except` 块中。
  2. 调度提交失败时，显式调用任务存储层接口，将任务标记为 `failed`（附带错误码 `dispatch_failed`）。
  3. 工具层返回结构化的错误响应，避免让底层调度异常直接打断 Agent 会话。

---

### 3. 【中风险】调度轮询异常被静默吞掉，缺少退避与可观测性
- **涉及文件**：
  - `core/background_task_worker.py:58-66`
- **问题现状**：
  - `_poll_loop` 中的主轮询逻辑在捕获 `Exception` 后直接执行了 `pass`。
  - 异常未记录到任务事件、Worker 状态或日志中；且轮询固定每秒 1 次，无退避机制。
- **潜在危害**：
  若底层数据库连接断开、权限异常或数据格式损坏，Worker 虽保持存活假象，但实际已丧失调度能力；持续高频轮询可能加剧系统资源消耗。
- **改进建议**：
  1. 记录结构化调度异常（包含错误类型、堆栈摘要与时间戳）。
  2. 引入指数退避（Exponential Backoff）机制，在连续遭遇故障时自动降低轮询频率。
  3. 维护 Worker 的最近一次心跳及健康状态监控指标。

---

### 4. 【中风险】提交成功后的账本写入异常导致“副作用完成但状态标记失败”
- **涉及文件**：
  - `core/commit_worker.py:217-247`
- **问题现状**：
  - 业务提交操作 `_commit_fn(task)` 成功完成后，任务被标记为 `COMMITTED`，随后调用 `self._ledger.mark_commit_terminal(...)`。
  - 若账本写入发生异常，控制流会跌入通用的 `except` 块，将状态覆写为 `COMMIT_FAILED` 并再次触发失败标记。
- **潜在危害**：
  记忆/数据实际上已写入成功，但对外呈现为执行失败。若上层据此进行错误重试，可能导致重复写入或数据状态不一致。
- **改进建议**：
  1. 实行两阶段隔离：业务写入成功即确立业务终态（Committed）；账本异常仅记录为 `ledger_sync_failed`，严禁回滚业务状态。
  2. 为账本写入建立独立的补偿机制或轻量重试队列。

---

### 5. 【中风险】视觉与具身工具服务缺少统一的服务级超时边界
- **涉及文件**：
  - `core/vision_service.py:15-70`
  - `core/somatic_service.py:168-220`
  - `core/somatic_appraisal.py:174-199`
- **问题现状**：
  - `VisionService.describe` 和 `SomaticService.process` 直接同步调用底层 LLM `invoke` 或外部观察器，自身缺少独立的服务级超时限制，完全依赖传入的 Client 全局配置。
- **潜在危害**：
  若外部 LLM 客户端配置未统一、网络中转出现长连接挂起，可能导致当前 Agent 轮次被具身/视觉操作长时间挂起。
- **改进建议**：
  1. 在工具服务入口显式传入或绑定统一的超时边界（Timeout / Deadline）。
  2. 在工具返回结构中明确区分 `timeout`、`service_unavailable` 与业务解析错误。

---

## 总结与后续动作建议

本次审核证实了高级模型代码审查模块（`start_code_review`）的闭环可用性。上述 5 项问题主要集中在**“异步调度健壮性”**与**“跨模块调用边界容错”**方面。

**建议后续配合 Codex 执行如下重构**：
1. 优先修复第 1、2 项（完善 Background Worker 的全局超时与 Dispatch 异常捕获）。
2. 在第 4 项中解耦 Commit 业务与 Ledger 账本状态，防止状态被误标记。
3. 补全各服务层调用的结构化日志与 Timeout 配置。

---

## 2026-09-08 整改结果

经逐项对照代码，5 项风险均已处理到当前阶段可实现的边界：

1. 后台审核任务写入统一总时限，`run_code_review` 在每轮模型调用和审核工具调用前检查截止时间；底层同步调用仍依赖客户端自身 timeout，未宣称可以强制杀死 Python 线程。
2. `start_code_review` 调度提交失败时把已创建任务标记为 `failed/dispatch_failed`，并返回结构化错误。
3. 后台轮询异常使用结构化日志记录，并对连续失败采用指数退避，恢复后回到默认间隔。
4. `CommitWorker` 在业务提交完成后先确立 `committed`；账本同步异常只记录为 `ledger_error`，不再把真实业务成功改写成 `commit_failed`。
5. 视觉观察和身体评价增加服务入口级 timeout，并分别返回可识别的超时失败状态。

本次整改新增针对性回归测试；未实现独立 OS 进程级强制终止和账本跨进程补偿队列，这两项仍属于后续增强。
