# 图片生成模块设计

## 1. 目标

让 Agent 在需要时调用本地图片生成能力，并把生成结果重新送回 Agent 的感知流程。

当前设想使用本地 ComfyUI。ComfyUI 负责加载模型、执行节点工作流和保存图片；Agent 只负责判断是否需要生成图片，以及提出生成请求。浏览器界面和 ComfyUI 工作流不是 Agent 的认知接口。

这是一项**框架层能力**。不同 persona 可以通过角色配置决定偏好的风格、是否主动创作和表达方式，但不能改变工具的状态真值与副作用边界。

## 2. 总体流程

```text
用户请求或 Agent 自主决定生成图片
        ↓
主 Agent 调用 generate_visual
        ↓
工具校验参数并选择已配置的工作流
        ↓
向本地 ComfyUI API 提交 workflow JSON
        ↓
ComfyUI 返回 prompt_id，任务进入排队或执行状态
        ↓
工具等待完成并读取输出图片元数据
        ↓
返回真实的任务状态和图片引用
        ↓
生成结果作为新的感知/工具结果进入 Agent
        ↓
Agent 向用户说明结果，或继续请求修改
```

ComfyUI 的浏览器页面只是一个客户端。代码也可以作为客户端，通过 HTTP 提交任务，并通过任务查询接口或 WebSocket 观察执行进度。

## 3. 工具边界

Agent 面向一个稳定的通用工具，例如：

```text
generate_visual(
    prompt,
    negative_prompt=None,
    width=None,
    height=None,
    seed=None,
    reference_image=None
)
```

工具负责：

- 校验提示词、尺寸、种子和参考图片引用。
- 把通用参数写入已配置的 ComfyUI API 工作流。
- 向 ComfyUI 提交任务并保存稳定的 `job_id` / `prompt_id`。
- 等待或查询任务状态。
- 只在图片真实生成后返回成功。
- 返回输出图片路径或受控引用、尺寸、格式、任务 ID 和来源。
- 明确返回排队、运行中、成功、失败或超时状态。

Agent 不应直接修改节点编号、采样器、模型文件名或工作流连接关系。那些属于工具实现和运行配置，便于以后替换 ComfyUI 或更换工作流。

工具参数中的 `upscale` 默认是 `false`。关闭时只提交普通文生图工作流，避免每次生成都执行放大采样；开启时才提交放大工作流。两份工作流可以使用不同的节点编号和字段映射，映射由 `config.py` 维护。

## 4. 工作流连接方式

在 ComfyUI 中搭好并验证一个工作流后，导出 API 格式的 workflow JSON。工具读取已配置的工作流模板，只修改允许暴露的输入字段，例如正向提示词、反向提示词、尺寸和种子。普通输出与放大输出使用两份独立的 API 工作流，由 `upscale` 开关选择；不在运行时删除节点或猜测节点连接关系。

最小连接关系如下：

```text
工具根据 upscale 选择 workflow_api.json 或 workflow_api_upscale.json
        ↓
替换允许修改的节点输入
        ↓
POST http://127.0.0.1:8188/prompt
        ↓
取得 prompt_id
        ↓
查询 /history/{prompt_id} 或监听 /ws
        ↓
读取 ComfyUI 输出信息
```

工作流模板、模型路径和 ComfyUI 地址属于本地运行配置，不写进角色卡，也不让模型自行决定。

## 5. 结果回流与经历记录

图片生成是一次带副作用的工具调用。工具返回的“成功”必须来自 ComfyUI 的真实结果，不能由 Agent 自己声称生成成功。

工具调用应沿用现有的：

```text
AgentAction → tool result / observation → ExperienceSlice
```

结果至少记录：

- 工具调用和任务 ID。
- 使用的参数摘要和工作流版本。
- 输出图片的路径或受控引用、格式、尺寸和哈希。
- 任务状态、失败原因或超时原因。
- 是否把图片重新交给视觉模型观察。

图片二进制不应直接写入 checkpoint 或普通经历文本。需要长期保存时，应由文件存储策略和图片引用机制明确管理；生成图片本身也不能自动变成长期认知。

如果 Agent 需要评价自己生成的结果，应把输出图片作为新的视觉感知输入，重新经过视觉观察流程。生成动作和“看见生成结果”是两个不同事件。

## 6. 失败和不确定性

以下情况必须如实返回：ComfyUI 未启动、连接失败、工作流参数无效、任务失败、超时、输出文件缺失或文件被替换。

失败不能伪装成已经生成图片，也不能因为单次生成失败让整个聊天进程退出。当前调用结束后清理临时上下文，保留可追踪的工具结果。

任务排队时间较长时，工具可以先返回 `queued/running` 和稳定任务 ID，再通过后续查询或后台事件报告完成结果。第一阶段也可以采用同步等待，但接口应保留任务状态，不把“调用函数”永久等同于“立即得到图片”。

## 7. 第一阶段验证闭环

先不接入主 Agent，单独验证一个最小文生图工作流：

1. 启动本地 ComfyUI。
2. 在浏览器中搭建并验证简单文生图工作流。
3. 导出 API 格式 JSON。
4. 用独立小程序替换提示词并提交 `/prompt`。
5. 根据 `prompt_id` 确认任务完成。
6. 读取并打开生成的图片，核对输出路径和元数据。
7. 测试 ComfyUI 未启动、任务失败和超时情况。

这个闭环通过后，再把调用逻辑封装成 `generate_visual` 工具，接入 Agent 的工具注册、`AgentAction` 和 `ExperienceSlice` 链路。

## 8. 后续扩展

后续可以在同一工具边界内增加：参考图生成、图片编辑、局部重绘、多候选输出、任务取消、后台生成、结果比较和生成图片的视觉复核。

这些扩展不应把 ComfyUI 节点细节暴露给主 Agent。主 Agent 看到的仍应是通用的生成请求、真实任务状态和图片引用。

## 9. 当前状态

第一阶段代码地基已接入：`core/comfyui_client.py` 负责 `/prompt` 和 `/history` 协议，
`core/image_generation_service.py` 负责参数校验、工作流字段白名单替换和输出文件哈希校验，
`tools/image_generation_tools.py` 注册了通用 `generate_visual` 工具，主循环已绑定图片生成服务。
没有工作流模板或字段映射时，工具返回 `configuration_missing`，不会伪造成功。

当前已配置两份工作流：`workflow_api.json` 是普通输出，`workflow_api_upscale.json` 是放大输出。
普通工作流的提示词、尺寸、种子映射到 `11.text`、`3.text`、`6.width/height`、`10.seed`；
放大工作流的映射仍为 `28.text`、`3.text`、`12.width/height`、`4.seed` 和 `25.seed`。
普通工作流只执行一次采样和一次输出，放大工作流才执行第二次采样和放大输出。ComfyUI 输出通过 `/view`
读取后复制到 `Card_slot/generated_images/`，不依赖 ComfyUI 安装目录。

2026-09-08 已完成一次真实最小闭环：ComfyUI `0.18.2` 返回 `prompt_id`，项目成功取得
PNG 输出并完成 SHA-256 校验。曾发现未提供 seed 时把 `null` 写入两个 KSampler 会导致
ComfyUI 400；现已改为保留模板默认 seed。视觉感知模块已经存在，但“看见图片”和“生成图片”
仍是两个独立能力；生图结果需要再次理解时，重新调用视觉工具。

## 10. 待完成项：单轮多张放大图会触发约 300 秒超时

- 登记时间：2026-09-09
- 登记人：如烟（Agent）
- 状态：**仅登记，未施工**。本轮未修改任何代码、超时配置或工作流文件。

### 已确认事实

- 2026-09-09 凌晨，Agent 在单轮内并行提交了两张 `upscale: true` 的生成请求
  （竖幅 832×1216，`workflow_api_upscale.json`）。
- 主人观察到的结论是：一次工具调用里生成两张放大的图，整体耗时超过约 300 秒后超时。
- 同一轮中 Agent 侧两次 `generate_visual` 均返回 `status=succeeded` 并各自产出文件；
  但整轮墙钟时间已超出上层等待上限，表现为调用链超时。两者并不矛盾：
  图片确实生成，调用方已先一步放弃等待。

### 未确定内容

- 约 300 秒是稳定的硬上限，还是本次的偶发表现；需要更多实测样本才能确认。
- 该上限位于哪一层（工具层等待、CLI 中间层、模型请求层）尚未定位。
- 普通（不放大）生成是否也存在相同限制，未测。

### 处理要求

- **单轮只提交一张放大图**，需要多张时拆成多个回合，不要并行。
- 放大工作流单张耗时较长，提交前应先向用户说明预计等待时间。
- 超时属于必须如实返回的状态，不能让 Agent 声称“已生成”而不核对工具返回。
- 若要根治，可考虑：任务改为异步提交 + 状态轮询（文档第 6 节已预留该接口方向）、
  或让工具在排队/运行阶段先返回 `queued/running` 和稳定任务 ID，由后续查询取回结果。
- 任何超时或等待上限的调整都属于系统配置改动，需主人确认后再动。
