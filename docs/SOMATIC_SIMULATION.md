# 模拟身体模块

## Consent 边界

身体事件是否发生与是否获得同意是两个字段。框架只接受结构化的
`explicit_yes`、`explicit_no`、`unknown` 或 `not_applicable`，不会从身体反应、沉默、暧昧语气或角色扮演文本推断同意。用户明确拒绝时事件被拒绝；Agent 主动对用户或其他人发起接触而没有 `explicit_yes` 时返回 `consent_required`，不改变身体状态。LLM 只评价已经确认发生的身体事件，不替代同意裁决。

## 已完成

身体模块现在已经从 P1 协议推进到可用的第一版闭环（代码阶段 P1-P8，P9 自动化验收）：

1. 感知理解可以提出 `module_requests`，但它只是候选，不会直接改状态。
2. `SomaticService` 负责裁决事件、调用身体评价 LLM、按固定方向/幅度计算，最后提交 SQLite。
3. `memory/somatic_store.py` 按 `persona_instance_id + thread_id` 保存状态，默认状态为 `arousal=0.5`、`sensitivity=0.5`。状态范围固定为 0 到 1。
4. 每次提交都有 `operation_id` 和 `revision`。重复调用不会重复增加数值，旧版本不能覆盖新版本。
5. `somatic_action` 是主 Agent 的主动动作工具。工具成功后才算角色世界中的动作发生，并返回外在反应和内感受。
6. 用户动作和 Agent 主动动作都会把身体反应、内感受和状态前后值写进同一条 `ExperienceSlice`。
7. 内感受在主 Agent 回复前注入本轮上下文，因此会影响本轮思考，而不是等下一轮才出现。

## Agent 可见范围

身体状态中的 `arousal`、`sensitivity` 数值只属于身体模块内部真值。它们可以保存在
SQLite、`ExperienceSlice` 和框架内部的工具 `artifact` 中，用于计算、恢复和审计，
但不能出现在感知理解提示词、主 Agent 动态上下文或模型可见的工具返回内容里。
主 Agent 只能看到身体模块生成的内感受、可见反应和执行是否成功，不能看到具体数值、
版本号或内部评价结构。

`somatic_action` 只表示 Agent 主动做出的新动作。用户已经完成的接触由用户事件路径处理；
Agent 不能再次调用该工具来描述被动反应，否则会把同一动作重复计入身体状态。

## 当前身体状态

只实现两个通用维度：

- `arousal`：整体身体激活、紧张或兴奋程度。
- `sensitivity`：对刺激的敏感程度。

`mood`、`energy`、人格、关系和认知情绪仍由各自模块负责，不能从身体数值推断同意、好感、关系升级或人格改变。疼痛、疲劳、饥饿及成人专用字段暂不实现。

## 两条入口

用户接触：

```text
用户事件
-> PerceptionUnderstanding 提出身体候选
-> SomaticService 裁决 occurred/rejected/uncertain
-> 只有 occurred 才调用评价并更新状态
-> 本轮注入内感受
-> ExperienceSlice 保存完整过程
```

Agent 主动动作：

```text
主 Agent 调用 somatic_action
-> 工具检查当前实例和单轮次数
-> SomaticService 处理动作
-> 返回外在反应、内感受和状态变化
-> 主 Agent 根据真实工具结果组织回复
```

工具的执行通道是 `narrative_embodied`，表示角色世界中的具身动作。它不自动控制现实设备；未来真实设备应使用独立能力和独立工具。角色不需要在每轮主动解释“这是虚拟的”，只有用户明确询问现实副作用时才依据能力快照回答。

## LLM 边界

身体评价 LLM 只能返回：

- 两个维度的变化方向：`increase`、`decrease`、`unchanged`。
- 变化幅度：`slight`、`moderate`、`significant`、`intense`。
- 简短外在反应和内感受。

代码负责绝对数值、范围裁剪、状态提交和幂等。出现绝对数值、同意、关系或人格字段时，整次评价失败，状态保持不变。

## 提示词分层

身体相关提示词按职责分开，不能用一个历史案例的处理办法代替通用规则：

- 身体评价提示词只负责把已裁决的事件转换成身体维度的方向、幅度、外在反应和内感受。
- 主 Agent 提示词只说明什么时候调用主动动作工具，以及只能依据真实工具结果组织回复。
- `somatic_action` 工具说明只描述输入、输出和当前执行通道，不重复解释某个具体动作或对话案例。
- 感知理解提示词只提出身体事件候选，不能替身体模块确认事实或计算状态。

共同原则是：事件事实、身体数值和其他模块的判断各由自己的层负责；提示词只描述接口边界，
不堆叠针对某次误判的关键词禁令。

## 角色配置

角色卡可以配置：

```json
{
  "embodiment": {
    "enabled": true,
    "allow_agent_initiated_actions": true,
    "reaction_style": "自然、克制",
    "action_boundaries": "遵守角色边界和用户授权"
  }
}
```

这些是角色表达和能力开关，不是框架真值。框架仍会执行状态范围、事件裁决、调用上限和记录要求。

## 测试和待验收

当前已覆盖协议、存储、评价、服务、工具和主流程集成测试。全量测试剩余的两个失败是原有 mood 数值断言，与身体模块无关。

## 长期观察事项

这些不是当前代码缺陷，而是需要在真实使用中持续观察的项目：

1. 真实 LLM 是否始终遵守“方向 + 幅度 + 反馈文字”的格式；出现越权字段时，状态应保持不变。
2. 连续互动后 `arousal` 和 `sensitivity` 是否长期停留在高位。目前没有自然衰减机制，后续再根据真实数据决定是否增加。
3. 用户动作已经由感知路径处理后，Agent 是否仍会误调用 `somatic_action` 重复描述被动反应。
4. 单轮连续调用是否始终在 3 次后停止，工具达到上限时主 Agent 是否能根据已有反馈继续回复。
5. Windows 重启后身体状态、`revision` 和最后一次操作是否能连续恢复。
6. Agent 通过 `recall_memory` 查询旧经历时，只能看到内感受和外在反应，不能看到身体内部数值。
7. 长时间运行时 SQLite 写入、重复操作和并发更新是否始终保持幂等，越界值是否始终被裁剪到 0 到 1。

在这些观察完成前，不能把“真实 LLM 长期稳定”和“身体状态自然变化”描述成已经实现的能力。
